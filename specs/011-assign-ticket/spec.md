# US-007 — Specification

**Phase:** 2 · **Story:** US-007 · **Feature:** `011-assign-ticket` · **Status:** reconciled against delivered code 2026-08-27, **awaiting review**

## Reconciliation — what changed under this spec since it was written

This spec was authored 2026-08-23, before `004`, `009`, `010` and `012` existed. Four of
its statements are now wrong, and they are corrected in a table rather than silently
edited, for the reason `009` learned the hard way: **a specification describing state that
does not exist makes every decision after it stand on invented ground.**

| # | The spec said | Actually | Consequence |
|---|---|---|---|
| 1 | `FK_Tickets_Assignee` was created by `009-create-ticket` | Created by **`004-auth-and-roles`**, 2026-08-27. `009` deferred all four FKs by name because `dbo.SupportUsers` did not exist | None for the design — the constraint exists now. It matters because it is why `009`'s seeder and one test were writing a fabricated assignee `Guid` for two features: an unenforced dangling reference that `004` made fail |
| 2 | The index is `IX_Tickets_Assignee`, created by `009` | It is **`IX_Tickets_AssignedToUserId`**, created by `004`, generated by EF from the FK rather than declared | The name in `data-model.md` was wrong, so "nobody adds a second one" was advice pointing at an index that does not exist. Corrected there |
| 3 | `dbo.SupportUsers.IsActive` is `bit NOT NULL DEFAULT 1`, created by `001-solution-skeleton` | `dbo.SupportUsers` was created by **`004`**, and `IsActive` has **no column default** | Deliberate, and it changes nothing here — BR-2.4 reads the column, it does not write it. `004` D-4 removed every column default because EF applies one whenever the property holds the CLR default, and for `bool` that is `false`: an entity being deactivated would have been stored as active. The identical defect shipped in `001` on `Customers.IsActive` |
| 4 | `dbo.AuditLog` carries the `Auth.Forbidden` rows for this feature | **`Auth.Forbidden` is not written by anything.** `004` AC-18 is deferred to `004b` — a gap in BR-9.4 | This one has teeth, and it decides where a BR-2 check lives. See *Where each BR-2 check lives* below |

Two further conflicts are **not** corrections — they are decisions that need the product
owner. They are Q-5 and Q-6 under *Open Questions*.

## Understanding

An unassigned ticket is not being worked by anyone. Assignment converts a shared list
into individual workloads and makes "who is handling this?" answerable at any moment.

This is the first story where the two roles genuinely diverge, so it is where the
authorization model stops being a diagram and becomes enforced behaviour.

**And that is now the load-bearing reason to build it.** `004` delivered the
`ManagerOnly` policy and `RequireAuthenticatedUser` as the fallback, and `ManagerOnly` has
**zero consumers in production** — no endpoint carries it. A policy that is registered but
never attached to a real endpoint is a policy that has not been verified, on exactly the
grounds `CLAUDE.md` states for any other guard: *a guard that has never been seen to fail
has not been verified.* `004` AC-7 proves the policy through a test-host endpoint, which
is honest and is not the same as proving it in the product.

## Where each BR-2 check lives

**This is the section to read before writing any code**, and it is the answer to the split
`CLAUDE.md` BR-6 requires: role-only checks are endpoint policies, data-dependent checks
are handler logic.

| Rule | Where | Why there and not the other place |
|---|---|---|
| Authenticated at all | **Endpoint** — `[Authorize]` | Already the fallback policy, but written explicitly because `AuthorizationSurfaceTests` enumerates endpoint *metadata* and a fallback policy is not metadata (`004` AC-10) |
| BR-2.1 · a Manager may assign anyone to anything | **Handler** | Not a policy, and this is the counter-intuitive one. `ManagerOnly` on the endpoint would refuse every Agent, and BR-2.2 says an Agent self-assigning unowned work is legitimate. So the endpoint cannot be role-gated at all |
| BR-2.2 · an Agent may assign an **unassigned** ticket **to themselves** | **Handler** | Needs the request body (`assigneeId`), the caller (`ICurrentUser.UserId`), **and** the ticket row (`AssignedToUserId`). A policy sees none of the three |
| BR-2.3 · an Agent may not reassign someone else's ticket | **Handler** | Same three inputs |
| BR-2.4 · the target must be an active `SupportUser` | **Handler** | A database read. Never a policy, and never a `CHECK` constraint — `data-model.md` says why |
| BR-2.5 · a `Closed` ticket cannot be assigned or unassigned | **Domain**, on `Ticket` | It is an invariant of the entity, not of the request. `012` put the same rule for status changes inside `Ticket.ChangeStatus`, and BR-1.5's terminality has to hold for every caller including a seeder |

### The consequence that decides it, and it is not a preference

**A handler-thrown denial is audited. A policy-level denial is not.**

`003`'s `AuditOutcomeClassifier` maps a `DomainException` whose code is
`DomainErrorCodes.Forbidden` to `AuditOutcome.Denied`, and `AuditBehaviour` writes that
row through `WriteIndependentAsync` — outside the transaction, so it survives the rollback
of the thing it refused. So a BR-2 denial raised in the handler produces:

```text
Action = Ticket.Assigned    Outcome = Denied    ActorUserId = the caller
EntityId = the ticket       TraceId  = the traceId in the 403 body
```

A `403` produced by the authorization middleware writes **nothing** — that is `004`
AC-18, deferred to `004b`, and reconciliation row 4 above.

So putting BR-2.2 and BR-2.3 in a policy would not merely be awkward; it would make
"an Agent tried to take a ticket that was not theirs" **absent from the audit log**, which
is the single event in this feature an investigation would most want. The split
`CLAUDE.md` mandates is also the split that keeps BR-9.4 satisfied for this feature while
`004b` is open.

**A new exception type is needed:** `DomainErrorCodes.Forbidden` exists (added by `003`)
and the classifier already keys on it, but there is no `ForbiddenException` class. `011`
adds it, in `Wasl.Domain/Common/Exceptions/`, the same shape as the other five.

## In Scope

Assign, reassign, and unassign; the BR-2 permission rules; the active-user
requirement; history rows; the assignee picker; optimistic concurrency.

## Out of Scope

| Excluded | Reason |
|---|---|
| Round-robin or load-based auto-assignment | Needs a workload model and a policy nobody has specified |
| Teams and queues | Single flat pool of support users in this release |
| Out-of-office handling | No requirement |
| Assignment notifications | Notification infrastructure is out of scope |
| Assignment changing the status | Deliberately not done — BR-2.7 |
| Status changes of any kind | `012-change-ticket-status`, **delivered 2026-08-26**. This feature moves ownership only |
| The `assignee` filter on the ticket list | `010-ticket-list-and-detail` for `me` / `unassigned`, `015` for the rest |
| User management (creating, editing, deactivating support users) | Not in the release. `SupportUsers` is seeded by `004` (ADR-005) |
| An audit row on a policy-level `403` | `004b`. This feature's denials are handler-thrown and therefore audited — see above. It does not close `004`'s gap and does not claim to |
| A rate limit on this endpoint | `004b` owns rate limiting, and it is unimplemented anywhere |

## Assumptions

| # | Assumption | If wrong |
|---|---|---|
| A-1 | An agent picking up unowned work should not need a manager | If triage is manager-only, BR-2.2 is removed and one check goes with it |
| A-2 | A ticket has one assignee, not several | Multiple assignees would need a join table and a different ownership rule |
| A-3 | Unassigning is a legitimate action, not an error | If tickets must always have an owner once assigned, `null` is rejected instead |
| A-4 | The support-user pool is small and seeded, so the picker needs no search or paging | If user management ever ships, `GET /api/support-users` becomes a paged endpoint and that is a breaking change for the client. Recorded as a known limitation, not designed around |
| A-5 | **Two users is enough to prove BR-2.** `004` seeded one Manager and one Agent | BR-2.3 — an Agent reassigning a ticket owned by *someone else* — needs a **third** user, because with two the "someone else" is always the Manager and the test cannot distinguish "not mine" from "belongs to a Manager". Either `011` seeds a second Agent, or AC-4 is proven against the Manager and the narrower case is recorded as untested. **This is Q-7** |
| A-6 | `013` is not built, so no timeline renders the history rows this feature writes | The `Assigned` and `Unassigned` rows are written and asserted in the database, not through a read endpoint. `TicketHistoryEventType.Assigned` and `.Unassigned` already exist in the enum (`009`), so no migration and no enum change |

## Open Questions

| # | Question | Working assumption |
|---|---|---|
| Q-1 | May an Agent unassign themselves from their own ticket? | Yes. Handing work back is legitimate, and the alternative traps an agent on a ticket they cannot progress |
| Q-2 | Should assigning to an inactive user be `400` or `404`? | `400`. The user exists; the request is invalid. `404` would suggest the id is wrong. Settled in `research.md` R-3, which also fixes the `type` and the `errors` key |
| Q-3 | Is `allowedTransitions` already precondition-aware when this feature ships? | **Closed by delivery.** `009` built the BR-1 map with its conditions and all 36 cells, and `Ticket.AllowedTransitions` passes `AssignedToUserId is not null` through. So assigning a ticket **does** change `allowedTransitions` without changing `status`, and AC-16 below asserts it rather than assuming it |
| Q-4 | Should the response tell the client whether the caller *may* assign, rather than the client mirroring BR-2? | Not in this feature. A server-authored capability flag is the better design and it is a change to the read shape, which `010` owns. Recorded so the mirrored rule in `FE-011-03` is visibly a stopgap |
| **Q-5** | **The frozen contract returns `assignee` as a nested object `{ id, fullName, role }`. Three delivered endpoints return three different shapes for the same concept.** `POST /api/tickets` and `GET /api/tickets/{id}` return a bare `assignedToUserId`; `GET /api/tickets` returns flat `assigneeId` + `assigneeName` with no role. Which shape does `PUT /assignee` return, and does anything change in `009`/`010`? | **Return the nested object, and change nothing else.** `011`'s contract is frozen and the frontend lane may already read it; the nested object is also the correct shape, because the client must not have to look a name up. The two older endpoints keep their shapes for now and the divergence is recorded as a known limitation with `010` owning the alignment. **This needs a ruling** — the alternative is aligning all three, which is a breaking change to two frozen contracts the frontend has already built against |
| **Q-6** | **The contract says a malformed route `Guid` is `400`. Delivered behaviour is `404`**, because ASP.NET Core's route constraint short-circuits before the action. It is a known defect owned by `002b` and recorded in the README | **Assert the observed `404` and cite the defect.** Writing a test for `400` would fail for a reason that has nothing to do with this feature, and writing one for `404` while the contract says `400` needs to be visible rather than quiet. `011` does not fix `002b` |
| **Q-7** | **A-5: does `011` seed a second Agent?** BR-2.3's precise case — an Agent reassigning a ticket belonging to *another Agent* — cannot be distinguished from "belonging to a Manager" with only two users | **Yes, seed a second Agent.** One row in `SupportUserSeeder`, idempotent like the other two, and it needs a third `Seed:*` password with no default. The alternative is AC-4 proven only against a Manager-owned ticket, with the narrower case recorded as untested — which is the weaker half of the rule going unproven |

## Acceptance Criteria

Numbering is fixed: `010`, `012`, and `013` all cite this feature's authorization proof.
AC-16 and AC-17 are **added** by this reconciliation; nothing is renumbered.

| # | Criterion |
|---|---|
| AC-1 | `PUT /api/tickets/{id}/assignee` with a Manager token assigns any ticket to any active user and returns `200` (BR-2.1) |
| AC-2 | An Agent may assign an unassigned ticket to themselves (BR-2.2) |
| AC-3 | An Agent assigning to any user other than themselves returns `403` (BR-2.2) |
| AC-4 | An Agent reassigning a ticket already assigned to someone else returns `403` (BR-2.3) |
| AC-5 | An Agent may unassign themselves from their own ticket |
| AC-6 | Assigning to an inactive user returns `400` (BR-2.4) |
| AC-7 | Assigning to an unknown user id returns `404` |
| AC-8 | Assigning or unassigning a `Closed` ticket returns `409` (BR-2.5) |
| AC-9 | Assignment writes an `Assigned` history row with the old and new assignee; clearing writes `Unassigned` (BR-2.6) |
| AC-10 | Assigning a ticket in `New` leaves its status unchanged (BR-2.7) |
| AC-11 | Assigning a ticket to the user it is already assigned to returns `409` |
| AC-12 | A stale `expectedVersion` returns `409` with `errors/concurrency-conflict` (ADR-006) |
| AC-13 | `GET /api/support-users` returns active users with id, name, and role |
| AC-14 | An unknown ticket id returns `404` |
| AC-15 | The picker lists active users and shows a clear `403` message when the action is not permitted |
| **AC-16** | **Assignment changes `allowedTransitions` without changing `status`.** An unassigned `Open` ticket returns `["Closed"]`; after assignment the same ticket at the same status returns `["InProgress", "Closed"]`. This is the criterion that proves BR-1.3's precondition is live rather than declared, and it is the reason the frontend must render the array it was given instead of holding a copy of the map |
| **AC-17** | **Every `403` in AC-3, AC-4 and AC-8 writes exactly one audit row** with `Action = Ticket.Assigned`, `Outcome = Denied`, a non-null `ActorUserId`, and a `TraceId` equal to the `traceId` in the response body. The row is present **although no business transaction committed** — BR-9.4's asymmetry, and the criterion that makes the handler-versus-policy decision above verifiable instead of argued |

## Edge Cases

From `testing/edge-cases.md`: unknown id, malformed id, inactive referenced user, no
token, wrong role, stale version, mutation of a closed ticket.

Specific to this story:

| Case | Expected |
|---|---|
| Manager assigns a ticket to themselves | Allowed; a manager is also an agent in practice |
| Assignee is deactivated after assignment | The ticket keeps the assignee. Deactivation does not retroactively strand tickets; reassignment is a deliberate act |
| Unassign an already-unassigned ticket | `409`, consistent with AC-11 — the request describes a change that is not a change |
| Agent unassigns a ticket assigned to **another** agent | `403` (BR-2.3). `null` is a target like any other, so removing someone else's ownership is a reassignment. Covered by `TEST-011-06`, not by a new AC |
| Agent assigns someone else to a `Closed` ticket — both `403` and `409` apply | `403`. The caller could not have performed this action on an open ticket either, and answering `409` first suggests that reopening would help — which it would not, because `Closed` is terminal (BR-1.5) |
| Stale `expectedVersion` **and** a forbidden action | `409` concurrency-conflict, checked first. The permission decision would otherwise be made against a ticket the client has not seen, and a `403` computed from data the caller cannot see is unfalsifiable. `research.md` R-6. **`012` shipped the same ordering** — the version check runs before the transition rules, as an explicit comparison rather than a caught `DbUpdateConcurrencyException`, and `011` follows it rather than re-deciding it |
| The current assignee is inactive and the caller sends the same id again | `409` unchanged (AC-11) before `400` inactive — a no-op is not an opportunity to enforce BR-2.4 retroactively, which would make an inactive assignee's ticket un-actionable |
| A ticket assigned to a now-inactive user is opened in the client | The strip shows that user; the picker does not list them. The current assignee is rendered from the ticket response, **never** looked up in the picker list, or it renders blank and reads as missing data |
| **The caller assigns a ticket to themselves and they are a Manager whose own account was deactivated** | Cannot happen through the API: a deactivated user cannot obtain a token (`004` checks `IsActive` at sign-in). It **can** happen with a token issued before deactivation, for up to 8 hours — `004` Q-F accepted that rather than adding a database read to every request. BR-2.4 still refuses it, because the check reads the *target's* row and the target is the caller |
